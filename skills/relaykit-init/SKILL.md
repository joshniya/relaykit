# Profile this codebase for relays

Every relay session starts by reading `.relaykit/PROJECT.md`. It is the "house rules": how to build and test
this project, what already fails, what to never touch. A wrong command here wastes every session after it, so
**verify, don't guess**.

## Steps
1. If `.relaykit/PROJECT.md` doesn't exist, run `relaykit scan` (or create the file from the outline below).
   Read it, plus `.relaykit/project.json`, the README, and every instruction file it lists (AGENTS.md,
   CLAUDE.md, GEMINI.md, .cursor/rules, copilot-instructions...).
2. **Verify the commands.** For install / build / lint / typecheck / test:
   - Run each (foreground, with a timeout; split anything over ~10 minutes into chunks — e.g. per test folder).
   - Never run anything that deploys, publishes, migrates a real database, sends messages, charges money, or
     needs secrets you don't have. Note those as owner-only instead.
   - Record: the exact command, how long it took, and the result. Fix wrong commands in the table and set
     Verified = yes. Add missing ones (e.g. a single-test command, a fast smoke test).
3. **Record the test baseline**: pass/fail counts and the NAMES of tests that already fail before any change, plus
   any flaky ones. Relay sessions compare against this, never against "zero failures".
4. **Architecture notes**: the entry points, the main modules and what they own, where tests live and how they're
   organised, how a request/command/event flows through the system, generated files that must not be hand-edited,
   build outputs that are committed. Use `file:line` references. Keep it to what a newcomer needs in their first
   hour — not a full map.
5. **Conventions**: formatting, naming, error handling, logging, test style, commit style; line endings if mixed.
6. **Hazards**: shared working trees (other people/agents editing), files that are huge, slow or flaky suites,
   test cross-pollution, secrets files, anything that bites. Each one with what to do about it.
7. **Owner-only**: deploys, releases, credentials, paid APIs, production data.

## Where to write
Update the tables and sections in `.relaykit/PROJECT.md` in place. Put everything that is NOT generated by the
scanner (architecture notes, baseline, hazards you found, conventions you learned) **below a line containing
`<!-- relaykit:keep -->`** — `relaykit scan --refresh` preserves that part verbatim.

Change no product code. When done, give the user a short summary: verified commands, the baseline, the top
hazards, and anything that needs them (missing tools, secrets, services).
